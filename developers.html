Post scheduled jobs into SubSub

When a job gets scheduled in your CRM, send it here. It arrives in SubSub as a job with its trades unassigned — which is the queue you open SubSub to clear — and you pick who does the work. One token, no SDK — and two ways in, because most of the systems that would send you a job cannot set an HTTP header.

The API is part of the Scale plan. Create your token in SubSub under My account → Profile → Connect your CRM. It is shown once, when you create it: SubSub stores only a fingerprint of it, so nobody here can read it back to you.

The endpoint

POST https://api.subsub.work/api/v1/jobs
Authorization: Bearer ssk_your_token_here
Content-Type: application/json

No header? Use the webhook address

Most CRMs and automation builders have a step that takes a URL and nothing else. There is no field for an Authorization header, so a token that can only arrive in a header cannot arrive at all. For those, the token travels in the path: 

POST https://api.subsub.work/api/v1/hooks/generic/<your-webhook-token>
Content-Type: application/json

SubSub builds that address for you — it is on the same panel as the token, beside it, at the moment you create it. It is not a weaker door: every check the header endpoint makes, this one makes. But the token is in the address, so treat the whole URL like a password.

The segment before the token names which system is sending, and that is the only thing it changes: SubSub reads that system's field names instead of its own.

UseForField names it expects
generic Zapier, Make, n8n, your own script — and any CRM not listed below SubSub's own, the ones in the tables on this page
jobnimbus JobNimbus automations Theirs. jnid, date_start, address_line1 and the rest — nothing to map.

A system with no entry of its own is not unsupported. It uses generic, and whatever sends the request maps its fields onto SubSub's on the way out — in Zapier or Make that is the webhook step's own field mapping, and it takes a minute. An entry is added above when somebody has a real payload from that system in front of them: inventing plausible field names would produce an integration that looks supported and fails silently on first contact, which is worse for everybody than saying generic.

Trades arrive as your own words

No CRM has a concept of a trade. What yours sends is a job type, a status and tags — your own words, and nothing in them means roofing until somebody says so. So the webhook address does not ask for trades. It reads those words and looks them up against the rules on your account, under My account → Profile → What your CRM calls things. Rules apply to every system you post from, so it is one list however many you connect.

A job whose words match nothing still arrives. It lands with no trades, the reply says so, and the word goes on a list on that same screen where one tap answers it. Refusing the job would be worse in the way that is hardest to notice: your CRM would not get a 200, so it would retry, so it would keep not getting one — and nobody would be told the work never reached SubSub. 

HTTP/1.1 201 Created

{
  "ok": true,
  "source": "generic",
  "duplicate": false,
  "jobId": "5b0f…",
  "trades": [],
  "needsTrades": true,
  "unmapped": ["type:Roof Replacement"],
  "url": "https://app.subsub.work/?job=5b0f…"
}

Watch needsTrades while you are still setting up. It is the difference between a job that landed ready to assign and one waiting on a word nobody has translated yet.

Two reads, for building an integration

Both take the same Authorization: Bearer header, and both are checked the same way a POST is — same plan gate, same token lookup. A read endpoint that is a lighter door is a lighter door.

EndpointWhat it answers
GET /api/v1/me Which account this token belongs to. Use it to check a key before anything depends on it — otherwise the first thing anybody learns about a wrong token is a job that did not arrive. It names the account, never a person: no person made the call.
GET /api/v1/trades Every trade id with a label, so a form can offer a list instead of asking somebody to type windows_doors from memory. It is the same list that validates trades on a job, so what you pick from and what is accepted cannot disagree.

Zapier

SubSub has a Zapier app, so a Zap can create a job without anybody pasting a URL: the token is a Zapier connection, and Trades is a dropdown rather than a text box. It uses this endpoint — Zapier can set a header, so it does not need the webhook address above.

It is a private app while it is new, which means you join it by invitation rather than finding it in Zapier's directory. Ask us for the link. If you would rather not wait, a Webhooks by Zapier step pointed at your generic webhook address does the same job today — the app is convenience and findability, not capability.

Required fields

Five things, and only five. Everything a job can carry is accepted, but requiring a square footage no CRM holds would make the integration fail over a number nobody needs — so required here means the job cannot do its work without it.

FieldTypeWhat it is
externalId required string Your own id for this job. This is what makes a retry safe — see below. Max 200 characters.
title required string What the job is called. Max 200 characters.
trades required string[] At least one. These become the unassigned slots you fill. See the list below.
date required string YYYY-MM-DD. The scheduled day.
address or propertyId required string Where the work is. Use propertyId for a building already on your account, address for anywhere else.

Optional fields

FieldTypeWhat it is
source optionalstring Which system it came from: jobnimbus, acculynx, servicetitan, housecall_pro, roofsnap or other. Defaults to other.
time optionalstring 24-hour HH:MM. Defaults to 07:00.
client optionalstring The homeowner or customer name.
area, zip optionalstring City and postal code.
scope optionalstring What the work involves. This is what a contractor reads on the work order.
sqft, stories optionalnumber Size of the building.
materialSource, materialsPaidBy optional stringWhere materials come from and who pays for them.
materialSupplier, materialBranch optional stringThe supply house and which branch of it. Accepted and stored; a job with neither is the ordinary case.
notes optionalstring Anything else worth carrying across.

Retries will not duplicate

Webhooks retry. If your CRM does not get a 200 or 201 back, it sends again — and without something to recognise the second delivery by, one scheduled job becomes four jobs on your roster and four contractors asked to show up on a Tuesday.

That is what externalId is for. Send the same one twice and the second call returns 200 with "duplicate": true and the id of the job that already exists. Nothing is created. You can retry as many times as you like. 

HTTP/1.1 200 OK

{
  "ok": true,
  "duplicate": true,
  "jobId": "5b0f…",
  "url": "https://app.subsub.work/?job=5b0f…"
}

Ids are scoped to your account and your source, so another SubSub customer using the same CRM with the same job number does not collide with you.

When something is wrong

Errors name the field, with a code your integration can branch on and a message for whoever ends up reading the log. 

HTTP/1.1 400 Bad Request

{
  "error": "invalid_request",
  "message": "Some fields were missing or not understood. See `errors` for which.",
  "docs": "https://subsub.work/developers",
  "errors": [
    { "field": "trades", "code": "unknown_trade", "message": "\"juggling\" is not a trade SubSub knows." },
    { "field": "date", "code": "invalid", "message": "date must be a real calendar day, as YYYY-MM-DD." }
  ]
}
StatusErrorWhat to do
400invalid_requestRead errors; each names a field.
400invalid_jsonThe body was not valid JSON.
401missing_tokenSend Authorization: Bearer <token>.
401invalid_tokenThe token is wrong or has been revoked. Create a new one.
403scale_requiredThe account is on Basic. The API is part of Scale.
403not_a_hiring_accountThis account is set up as a subcontractor, so it has nobody to assign.
404property_not_foundNo building with that propertyId on this account.
429rate_limited300 requests per minute per account. Back off and retry.

Keeping the token safe

  • It is shown once. SubSub stores a SHA-256 of it, not the token, so it cannot be read back — by you or by us. Lost it? Revoke it and make another.
  • It belongs to one account and can only create jobs on that account.
  • Revoke it any time under My account → Profile. Anything using it stops immediately; jobs it already created stay, because that work is real.
  • Keep it server-side. Anyone holding it can create jobs on your account.

What happens next

The job lands on your Jobs screen with its trades unassigned, and it counts toward Unassigned trade slots on your dashboard. From there it is the ordinary SubSub flow: assign a contractor per trade, or ask several of yours to quote it, and SubSub checks their insurance and licence before the work order goes out.
